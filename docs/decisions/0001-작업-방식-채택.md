# 0001. 설계·실행 세션을 나누고, ADR·보고서·fileaudit·git 규칙으로 일한다

- 상태: **확정**
- 날짜: {{YYYY-MM-DD}}
- 관련: `CLAUDE.md`, `.claude/skills/`, `claude-project-template`(출처)

## 배경

여러 세션과 도구(Cowork, Claude Code)가 같은 저장소를 번갈아 만진다. 대화 기록은 세션이 끝나면 사라지고, 에이전트가 "고쳤다"고 보고한 것과 실제로 바뀐 것이 다를 수 있다. 몇 주 뒤에 "왜 이렇게 했나"를 복원하려면 결정·결과·상태·변경이 각각 한 곳에 남아야 한다.

## 고려한 대안

| 대안 | 장점 | 단점 | 채택 |
|---|---|---|---|
| 대화 기록과 커밋 메시지만 남긴다 | 추가 문서 없음 | 결정 이유와 결과가 흩어지고 검색이 안 된다 | |
| 이 방식(ADR + 보고서 + STATUS + fileaudit + git) | 사실마다 정본이 하나, 검증 가능 | 문서 작성 비용, 갱신을 거르면 낡는다 | ○ |

## 결정

- **역할**: 설계·해석·판정·ADR은 설계 세션, 실행은 실행 세션. 실행 세션은 설계 판단을 하지 않고 "판단 필요"로 멈춘다. 한 단계는 한 세션에서 끝낸다.
- **사실의 정본**: 결정 = `docs/decisions/`, 결과 = `reports/`, 상태 = `docs/STATUS.md`, 변경 검증 = `.changelog/`. `CLAUDE.md`에는 바뀌는 상태를 적지 않는다.
- **변경 이력**: git(버전·백업)과 `tools/fileaudit.py`(주장 대 실제 검증)를 함께 쓴다. `snapshot`·`diff --commit`은 설계 세션만, 실행 세션은 `record`만 한다.
- **git**: 커밋·푸시는 사용자가 요청할 때만. 메시지에 "무엇을"과 "왜", 큰 결정이면 ADR 번호.
- **ADR 기준**: 나중에 "왜?"가 나올 선택만 쓴다. 결과 판정은 보고서에 쓴다.
- **점검**: 문서 정합성은 `tools/lint_docs.py`, 보고서 수치는 `tools/check_numbers.py`로 단계 마무리에 점검한다. 강제 장치는 아니다.

## 영향

- 단계를 마칠 때 보고서, STATUS.md 갱신, fileaudit 기록이 한 묶음의 마무리 체크리스트다(`run-stage-instructions` 스킬).
- 이 ADR을 바꾸려면 새 ADR로 대체한다.

## 되돌리는 조건

문서 갱신 비용이 얻는 것(복원 가능성)보다 커져서 STATUS.md나 ADR이 실제로 쓰이지 않게 되면, 문서를 늘리지 말고 이 방식의 어느 부분을 줄일지 다시 정한다.
